### 显存压力
这是一个非常典型的**显存占用峰值（Memory Spike）**问题。虽然显示有 10.75 GiB 的 Free 空间，但 torch.cat(flat_grads) 操作瞬间尝试分配 11.49 GiB，直接导致超限。

1. 深度剖析：为什么显存够却依然 OOM？
物理 vs. 逻辑显存：

报错显示 GPU 1 的总负载中，Process 3654097 占用了 107.08 GiB。当你尝试 torch.cat(flat_grads) 时，PyTorch 需要申请一块连续的 11.49 GiB 物理显存。
关键点：即使系统报告有 10.75 GiB 空闲，但这些空间可能被碎片化（Fragmentation）了。torch.cat 是一个非原地操作（Non-inplace），它要求分配一块完整的新内存来存储拼接后的结果，如果碎片无法拼接，分配器就会报错。
计算图的“瞬时膨胀”：

报错定位在 steps_parl.py 第 162行 return torch.cat(flat_grads)。
原因：flat_grads 是一个列表，里面存了模型所有参数的梯度。在执行 cat 的一瞬间，你会同时存在两个内存占用：
flat_grads 列表本身持有的所有梯度张量（它们已经在显存里了）。
拼接结果所需的额外 11.49 GiB（这是新申请的）。
隐式梯度路径的特殊性：你在计算 implicit gradient，这时不仅有常规的梯度，还有由 HVP（Hessian-Vector Product）产生的额外参数存储，这让本就紧张的显存再次被压迫。
2. 为什么显示 Free 却分配失败？
在你的系统中，Process 3654097（看来是主训练进程）已经占用了 107GB 的基础位。剩下的显存其实是“脆弱平衡”。

在调用 implicit_gradient 时，PyTorch 会进行一系列矩阵运算（CG 迭代）。这些中间张量在显存操作中产生的临时占用，往往在 nvidia-smi 监控的 Used 字段中更新有延迟。换句话说，你在报错那瞬间，其实显存已经撑爆了。

### 提速优化


#### 方案一：采用 PyTorch 2.x `torch.compile` 算子编译优化

* **原理**：
* PyTorch 2.x 引入的 `torch.compile` 可以通过算子融合（Operator Fusion）和图优化（Graph Optimization），减少 Python 解释器开销以及反复启动 CUDA Kernel 的时间。在 PPO 内循环中，由于模型结构固定、输入张量形状相对规整，编译带来的加速效果非常明显。


* **实施步骤**：
1. 在定义好 Actor 或 Critic 模型之后、进入训练循环之前，使用 `torch.compile` 进行包裹。
2. 例如在 `src/llm/qwen_module.py` 或训练初始化阶段，对模型进行编译：
```python
# 针对训练图进行优化，reduce-overhead 适合减少小 batch 的内核启动开销
self.actor = torch.compile(self.actor, mode="reduce-overhead")

```




* *注意*：首次编译时会有一小段预热时间（JIT 编译耗时），属于正常现象，编译完成后后续每轮迭代的耗时会显著下降。



---

#### 方案二：提升异步评分器（Scorer）的并发度

* **原理**：
* 在外循环中，调用外部评分 API（如 DeepSeek 或兼容接口）对生成的 XML 文本打分是串行或低效并发的重灾区。如果并发数不够，大量时间会浪费在网络等待（I/O 阻塞）上。


* **实施步骤**：
1. 打开 `configs/default.yaml` 文件，找到 `scorer` 或 `metric` 相关的配置段。
2. 将 `api_concurrency`（并发数）从原有的较低值（如 4 或 8）大幅提升至 **16** 甚至 **32**（需确保后端 API 服务器能够承载）。
3. 调整 `api_timeout`（超时时间）和 `api_retries`（重试次数），确保在高并发下偶尔由于网络抖动导致的请求失败能够平稳重试，而不拖慢整体流水线。



---

#### 方案三：引入 vLLM 加速 Rollout（生成阶段）

* **原理**：
* 在 PPO 的外循环中，用当前的 Actor 批量生成（Rollout）文本是耗时大户。标准 Hugging Face 逐个 Token 生成的效率较低。如果能引入 **vLLM** 引擎，利用其 **PagedAttention（分页注意力机制）** 和连续批处理（Continuous Batching），生成速度可以提升数倍。


* **实施步骤**：
1. 检查您的项目配置文件 `configs/default.yaml` 中关于 `qwen_module` 的选项，部分配置里支持将推理后端切换为 `vllm`。
2. 如果代码层支持 vLLM 接入，确保安装了 vLLM 依赖，并在推理/生成阶段调用 vLLM 异步推理服务，将大批量 Prompt 一次性高吞吐送入显存生成，从而把原本占大头生成时间压下来。



---

#### 方案四：序列长度裁剪与 Pad 最小化（Length Optimization）

* **原理**：
* Transformer 计算量和显存随序列长度 $N$ 呈平方级（$N^2$）增长。SUMO 的 XML 生成如果包含过多冗余注释、长文本或格式化空格，会导致序列变长，拖慢整体训练。


* **实施步骤**：
1. 在 `configs/default.yaml` 中重新审视并收紧 `prompt_max_len` 和 `generate_max_len`。确保在满足任务需求（如输出合法的 1.nod.xml、1.edg.xml、1.con.xml 片段）的前提下，不生成无意义的冗余文本。
2. 检查评测和生成时的填充（Padding）策略，尽量让同一批次（Batch）内的文本长度相近，避免单条极长文本导致整个 Micro-Batch 发生严重的 Padding 浪费。

#### 初步分析
```
1. 领域知识硬性违规 (XML 规范层)
模型对 SUMO 的特定 XML Schema 缺乏遵循能力，表现为严重的“领域幻觉”：

标签伪造：将标准的 <connections> 和 <connection> 错误地写成 <con>、<conn> 或 <conns>，这些非法标签直接导致 netconvert 解析器报错。
属性名拼写错误：频繁使用自定义或不符合规范的属性名（如 fromlane 代替 fromLane，甚至使用 toname 这种完全不存在的属性）。
XML 结构截断：长序列生成时，XML 关闭标签（如 </connections>）经常缺失，导致文件语义完整性破坏。
2. 逻辑约束执行失败 (指令遵循层)
模型在处理“删除特定转向但保留其余”的逻辑时，往往采取了“全删”或“全留”的极端策略：

禁止转向执行紊乱：指令要求删除 A->B 转向，模型有时会保留该转向，有时则误将相关联的正常连接（如 A->C）一并删除。
连接完整性缺失：模型输出的连接（Connections）通常只有 4-12 条，远低于要求的 15 条完整逻辑连接。这种“偷懒”导致模型即使拓扑正确，也无法生成合法的路网文件。
3. 可执行流程闭环丢失 (工程能力层)
模型将生成任务仅仅理解为“写文本”，而忽略了“生成工程文件”的意图：

缺失执行脚本：绝大多数输出缺乏 netconvert 生成命令（参数缺少 --output-file 或路径引用占位符），导致 Evaluator 无法进行下一步的 GUI 验证。
分段输出不规范：未将 nod.xml、edg.xml、con.xml 按照标准独立输出，使得评估层无法切分并验证各个独立文件的合法性。
结论：目前的模型表现出**“结构拓扑语义准确，但工程协议遵循严重失效”**的特征。这说明模型目前通过 PPO 学到的权重更多是在拟合“看起来像个路网”的文本分布，而没有学到“这些文本必须通过 XML Schema 约束”的 hard constraint。对于下一步的改进，单纯增加训练轮数可能无法根治，建议在 Prompt 中通过 Few-shot 提供极小规模但极规范的 Schema 片段，并强制要求模型输出 netconvert 命令。
```

#### 解决方案

##### 1. 结构化约束 Prompt 优化 (即时生效)
目前的低分主要源于模型对 SUMO XML 格式的理解偏差。在运行 `run.py` 进行 `Generating fresh rollout data` 之前，必须在 System Prompt 或 Prompt Template 中强制植入 **Schema 约束**：

*   **新增强制规则**：
    *   “禁止使用 `<con>`、`<conn>` 或非标准 XML 标签，必须仅使用 `<connections>` 和 `<connection>`。”
    *   “针对每一条 `connection`，必须包含完整属性：`from`、`to`、`fromLane`、`toLane`。”
    *   “输出必须包含 netconvert 命令：`netconvert --node-files 1.nod.xml --edge-files 1.edg.xml --connection-files 1.con.xml -o 1.net.xml`。”
*   **示例注入 (One-shot)**：在 Prompt 中提供一个包含 5 条连接的 **完美格式范例**，让模型在生成时以此为模版（避免模型在 Token 生成过程中产生“结构漂移”）。

##### 2. Action Mask 的逻辑边界修正 (必须执行的修复)
根据测试验证，`action_mask` 覆盖不足是性能问题的核心。在后续代码修复时，应执行以下调整：

*   **动态起始位置对齐**：修改 `action_mask` 的生成逻辑，不再根据 `token` 索引截断，而是通过 **Regex 探测 XML 标签的实际生成位置**。
    *   **修正点**：查找第一个 `<node` 和最后一个 `</configuration>` 的 token 索引作为 `start` 和 `end`。
*   **确保全覆盖**：对于所有在 `node/edge/connection` 标签内的 token，将其 `action_mask` 强制置为 `1`。

##### 3. Reward 机制的双重过滤 (降低噪声)
目前的 Reward 为 `-0.02` 左右，噪声极大。建议引入 **“结构合法性奖励叠加”**：

*   **增加验证奖惩**：在调用 `rightapi` 评分前，先运行轻量级的 `lxml` 代码块校验：
    *   如果由 `lxml` 验证 XML 格式非法（如标签未闭合），直接给予 -1.0 惩罚。
    *   这能帮助模型在 PPO 训练中迅速分辨“可解释代码”与“废话文本”。
*   **归一化处理**：鉴于目前 reward 有负值且方差很大，在传给 PPO 前进行 `(r - mean) / std` 归一化，防止 Critic 陷入梯度爆炸（日志中 `min=-7.4` 证明梯度确实在剧烈波动）。

##### 4. 辅助测试验证方案 (后续验证)
在你决定改动代码前，可以使用下面这个轻量级的验证逻辑检查当前模型是否处于“可训练状态”：

```python
# 简单的 XML 结构检查逻辑 (用于 test/validate_fixes_runtime.py)
def check_xml_completeness(response):
    # 强制检查关键 XML 组件
    required = ["<connections>", "<connection", "fromLane", "toLane"]
    return all(r in response for r in required)

# 在 run.py 的 pipeline 中注入此验证逻辑
# 如果检查失败，在将数据喂给 PPO 之前通过 reward_model 强制赋予负分，
# 这样即便模型还没学好格式，也会因为“格式错误”而被迅速剔除出 batch。
```

##### 实施建议顺序：
1.  **第一步 (Prompt)**：更新 Prompt 模板，增加 Few-shot XML 规范强制约束。
2.  **第二步 (Validation)**：在 reward 计算函数中加入 `lxml` 格式检查，将非法 XML 的 Reward 强制置为 -1。
3.  **第三步 (Engineering)**：待验证 Prompt 和 Reward 过滤有效后，再通过修改 `steps_parl.py` 修复具体的 `action_mask` 获取逻辑。
