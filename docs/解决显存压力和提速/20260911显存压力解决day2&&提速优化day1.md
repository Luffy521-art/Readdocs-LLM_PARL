### 提速方法
* **引入历史数据滑动窗口（Sliding Window），彻底切断 Re-scoring 的膨胀瓶颈**：日志中显示每一轮都要 `Evaluating all 64 accumulated samples`，随着外循环轮次增加，历史样本越积越多，这一步的耗时会线性暴涨。将历史数据缓存限制在一个固定大小（例如只保留最近 2 轮的共 64~128 条样本），多余的直接抛弃或固定不再全量重打分，这一项就能直接省下数分钟。
* **精简 PPO 内循环更新次数（`inner_updates: 5 → 2`）**：PPO 阶段占了总耗时的近一半（9分多钟）。在策略对齐初期，没必要每一轮都死板地做 5 次完整的梯度内循环更新。将 `inner_updates` 调为 2 或 3，配合更大的微批次，能让 PPO 阶段的耗时从 9 分钟直接腰斩至 **3.5 ~ 4 分钟**。
* **极限压缩生成长度上限（`generate_max_len: 1024 → 768`）**：SUMO 的 XML 路网结构本质上是有高度规律的代码片段，不需要冗长的文本。将最大生成长度从 1024 压到 768，不仅能让生成速度提升 30%，还能在线性上减少后续 Attention 计算和二阶导数图的显存与时间开销。
* **全面开启 PyTorch 2.x 动态图编译优化（`torch.compile`）**：在 Qwen 的 Actor、Critic 模型加载后，显式加上 `model = torch.compile(model, mode="reduce-overhead")`。由于 H20 运行的是静态形状的 PPO 批次，算子融合后可以把 GPU 内核启动的闲置开销降到最低，带来额外的 20% 整体加速。
* **对齐 API 异步打分的极限批处理**：将打分并发度（`api_concurrency`）拉高到 64，并让客户端以真正的异步大包形式投递请求，把原本拖后腿的网络等待压扁到 20 秒以内。

### 详细方案

以下是针对**SDPA 与 `torch.compile**`、**滑动窗口缓存**以及**PPO 内循环微调**这三大提速模块的**详细落地修改方案**。你可以直接按步骤在项目中实施。

#### 一、 模块 1：落地 PyTorch SDPA 与 `torch.compile` 编译加速

为了让模型在前向传播和生成时自动利用底层高效算子，我们需要在模型初始化或加载的入口处显式激活它们。

##### 1. 修改位置

找到你的模型加载与初始化模块（通常在 `src/llm/qwen_module.py` 或模型工厂类中）。

##### 2. 具体修改方案

在模型的初始化函数末尾，或者在模型加载完成后，插入以下代码：

```python
import torch

# 1. 显式开启 PyTorch 原生高效 Attention 后端（替代 FlashAttention-2）
torch.backends.cuda.enable_flash_sdp(True)
torch.backends.cuda.enable_mem_efficient_sdp(True)
torch.backends.cuda.enable_math_sdp(True)

# 2. 对策略模型 (Actor) 启用 torch.compile 动态编译
# 注意：必须在模型已经 .to(device) 并且设为训练/评估状态之后调用
if hasattr(torch, "compile"):
    info("[Optimization] 正在启用 torch.compile 对策略模型进行算子融合编译...")
    # 使用 reduce-overhead 模式，针对静态/半静态批次极度高效
    self.actor_model = torch.compile(self.actor_model, mode="reduce-overhead")

```

#### 二、 模块 2：引入滑动窗口缓存（斩断 Re-scoring 线性膨胀）

通过对历史 rollout 样本进行 FIFO 队列截断，彻底解决随着训练轮次增加、历史数据越积越多导致的重复前向计算卡顿。

##### 1. 修改位置

找到负责管理和累积训练样本的主循环文件（如 `run.py` 或 pipeline 中的样本收集器）。

##### 2. 具体修改方案

在样本累加和重打分（Re-scoring）的逻辑处，加入窗口限制：

```python
# 设定历史样本滑动窗口的最大容量
MAX_WINDOW_SIZE = 128

# 假设你的历史样本存储在一个列表或缓存队列中：
# self.accumulated_samples = []

def append_and_trim_samples(new_samples):
    # 1. 追加新生成的 rollout 样本
    self.accumulated_samples.extend(new_samples)
    
    # 2. 如果超出窗口大小，按先进先出（FIFO）原则截断，只保留最新的部分
    if len(self.accumulated_samples) > MAX_WINDOW_SIZE:
        self.accumulated_samples = self.accumulated_samples[-MAX_WINDOW_SIZE:]
        info(f"[PARL] 触发滑动窗口截断，当前历史样本池大小已精简至: {len(self.accumulated_samples)}")

```

* **效果**：后续的 `Evaluating all accumulated samples` 永远只会在固定大小（如 128 条）的最新样本池上运行，彻底消除了线性增长的耗时黑洞。

#### 三、 模块 3：微调 PPO 内循环与生成配置

将过分激进的内循环次数从 `1` 适当调优，并确保生成长度和并发度拉满。

##### 1. 修改位置

####  改后报错1

##### 1. 报错现象

在启动训练时，控制台抛出 `RuntimeError: Error(s) in loading state_dict for Actor:`，并伴随大量 `Missing key(s)`（缺少键）以及 `Unexpected key(s)`（意外键）的错误。其中所有的模型层键名都被强制加上了 **`_orig_mod.`** 前缀（例如 `model._orig_mod.model.layers.0...`）。

##### 2. 根本原因

在模型初始化的 `__init__` 阶段过早地调用了 **`torch.compile()`**。
PyTorch 的 `torch.compile` 底层（Dynamo）会使用动态图重新包装模型结构，导致其参数名称被注入了 `_orig_mod.` 封装层。随后，当代码执行检查点恢复（`load_state_dict`）时，保存的权重仍然是原始命名，两者的键名无法对齐，从而触发加载失败。

##### 3. 解决方法

采用**时序解耦与延后编译**的工程策略：

* **移除早期编译**：从模型构造函数 `__init__` 中剥离 `torch.compile`，确保在加载检查点权重时模型保持原始的干净结构。
* **建立显式编译方法**：在模块中封装一个专门的激活方法（如 `compile_actor_model()`）。
* **延后触发时机**：在主训练脚本中，严格等待 Checkpoint 状态字典加载完毕、模型权重恢复正常后，再手动调用该编译方法激活 Triton 算子融合。
