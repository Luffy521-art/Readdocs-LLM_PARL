## 新的提速方案

综合前述日志、各阶段耗时分析（稳定在约 16.5 分钟/轮）以及当前的系统架构，单纯靠底层的 PyTorch 算子和配置微调已经触及天花板。要将总耗时从当前的 ~16.5 分钟压榨到目标区间（**5-8分钟/轮**），必须针对当前流水线中的**串行阻塞点**和**冗余计算**实施颠覆性的“手术式”重构。

以下是针对性的瓶颈剖析与全新的 **“多级解耦与异步化”提速方案**：

---

### 一、 核心瓶颈剖析

1. **AI 外部打分与验证串行等待（累计占比 ~25%）**
* 尽管配置了 `api_concurrency: 64`，但在每次 PARL 重采样打分（8条）和测试集评估（16条）时，代码依然会同步等待所有网络请求返回才能往下走。网络延迟加上大模型生成，单次评估往往需要消耗 1.5 到 2.5 分钟。


2. **冗余的历史 Re-scoring（重打分）开销（累计占比 ~20%）**
* 代码在每次 PARL 隐式梯度更新后，会触发：`Re-scoring accumulated data with PARL reward model`。即使引入了 `MAX_WINDOW_SIZE = 128` 滑动窗口，对这几十甚至上百条历史长序列调用 Qwen 做 Teacher Forcing 提取 `hidden_states` 并在本地前向传播打分，依然需要消耗大量计算时间。


3. **PPO 内循环与 PARL 的强同步串行（累计占比 ~55%）**
* 生成、PPO 策略更新、PARL 隐式梯度计算（含 CG 共轭梯度迭代）、历史重打分全部堆在同一个单进程主循环中，GPU 在部分 I/O 或等待阶段处于闲置或负荷交替状态。



---

### 二、 全新提速方案：四维手术式改造

#### 方案 1：推行“异步影子打分”与评估频率解耦（预计节省 3~4 分钟/轮）

* **降低评估频次**：当前 `eval_every: 1` 意味着每轮外循环都要跑一次 16 条样本的测试集打分。建议将 `eval_every` 调整为 **3 或 5**。训练初期模型处于摸索阶段，频繁评估毫无意义，反而白白浪费宝贵的网络 I/O 时间。
* **异步 API 打分缓存池**：将 Scorer API 的请求改为异步非阻塞队列。允许 PPO 训练与外部 API 打分准异步解耦，避免因网络抖动导致整个训练流水线强行暂停。

#### 方案 2：废弃全量历史 Re-scoring，改用“流式增量打分”（预计节省 2~3 分钟/轮）

* **现状**：每次窗口有新样本进来，都要把整个窗口（最多 128 条）拿出来重新跑一遍 Teacher Forcing 提取 `hidden_states`。
* **改造**：既然采用了 FIFO 滑动窗口（容量 128），新 rollout 进来的数量通常很少（如 64 条或 8 条），**历史已经打过分的样本其 PARL 奖励应当直接复用缓存**，绝对不能每轮对所有历史样本进行全量二次前向计算。只需对新产生的 `delta` 样本计算奖励并拼接到历史缓存中。

#### 方案 3：压榨 PPO 内循环与 PARL 的并发 / 微批次上限（预计节省 2~3 分钟/轮）

* **合并冗余前向**：在 `train_ppo` 阶段，检查是否有不必要的全量概率二次前向推断。
* **精简 PARL CG 迭代数**：当前 `parl_cg_iters`（共轭梯度迭代次数）设为了解耦的配置。若显存和精度允许，可将其压紧至 `1`（当前已部分采用），并在单条长序列裁剪上严格限制最大长度（如当前已做的 `parl_max_seq_len = 512`），防止二阶 Hessian 矩阵计算引发显卡微架构层面的频繁同步等待。

#### 方案 4：引入多卡显存异步流水线（Pipeline Parallelism）

* 结合当前多 GPU 环境（如配置中涉及 `actor_device`, `ref_device`, `parl_device` 分布在不同卡上）：
* **让 Actor 生成和 PARL 训练物理异步**：当卡 A 正在进行下一轮的 PPO 策略生成时，卡 C 异步在后台利用上一轮的数据进行 PARL 奖励模型的梯度更新，实现计算吞吐的“双卡双工”。

## 详细方案

为了将每轮总耗时从当前的约 16.5 分钟稳步压榨至 **5-8 分钟**的目标区间，以下为您将上述“四维手术式改造方案”转化为**工程可落地、具备具体代码逻辑与配置指导**的详细实施方案。

---

### 方案一：推行“评估频率解耦与异步化”（预计节省 3~4 分钟/轮）

#### 1. 配置文件降频

避免每一轮外循环都执行高开销的 16 条测试集评估和同步网络请求。

* **修改文件**：`configs/default.yaml`

```yaml
# 将评估频率从每轮一次调低，释放测试集网络等待
eval_every: 3   # 建议设为 3 或 5

```

#### 2. 异步非阻塞 API 队列化改造

通过 `asyncio` 异步并发控制，避免网络阻塞拖累主线程。

* **修改位置**：`src/metrics/base.py`（或您的 API 客户端核心调度处）
* **核心逻辑**：

```python
import asyncio

async def async_compute_rho_batch(prompts, responses, session, api_base, headers, semaphore):
    """使用信号量控制并发的异步请求池，防止瞬时网络拥堵挂起"""
    async with semaphore:
        payload = {"prompts": prompts, "responses": responses}
        try:
            async with session.post(api_base, json=payload, timeout=60) as response:
                if response.status == 200:
                    return await response.json()
                else:
                    return {"score": 0.0, "reason": f"HTTP {response.status}"}
        except Exception as e:
            return {"score": 0.0, "reason": str(e)}

```

### 方案二：废弃全量历史 Re-scoring，改用“流式增量打分”（预计节省 2~3 分钟/轮）

#### 1. 核心原理

当前的性能黑洞在于：每次窗口有新样本进来时，代码会把整个滑动窗口（最多 128 条）全部重新跑一遍 Teacher Forcing 提取 `hidden_states`。实际上，**历史样本的 `hidden_states` 已经计算过并存在缓存中**，只需对**本轮刚产生的新 rollout 样本**计算一次特征和奖励，然后拼接到历史缓存即可。

#### 2. 代码落地实施方案

* **修改文件**：`src/pipeline/runner_LLM_new.py`
* **具体改造**：在 Re-scoring 的循环处，引入样本唯一哈希或索引标识，复用历史缓存。


### 四、 引入多卡异步流水线（Pipeline Parallelism）

#### 1. 多卡分工解耦思路

当前您的环境配置了多张 GPU（如通过启动脚本分配了 `actor_device`, `ref_device`, `parl_device`）。为了彻底打破“生成完才能训练，训练完才能打分”的串行魔咒：

* **GPU 0 (Actor)**：专职负责 PPO 的 rollout 高速生成。
* **GPU 1 (Critic / Ref)**：专职负责价值网络与参考模型计算。
* **GPU 2 (PARL)**：在后台开辟一个独立的轻量异步线程/进程，当 GPU 0 生成完新数据并丢进共享队列后，GPU 2 异步在后台执行 PARL 奖励模型的梯度更新，不阻塞主生成链路。

#### 2. 简易异步化落地（非阻塞后台更新）

在 `runner_LLM_new.py` 的外循环中，将 PARL 的隐式梯度更新丢给后台线程执行，主线程直接进入下一轮的 PPO 生成：

```python
import threading

def background_parl_update(parl_context, policy_model, databatch, labels, cg_iters):
    """在后台线程异步执行昂贵的 PARL 隐式梯度更新，实现计算重叠"""
    try:
        parl_context.compute_parl_implicit_gradient(...)
        parl_context.optimizer.step()
        parl_context.optimizer.zero_grad()
    except Exception as e:
        print(f"后台 PARL 异步更新异常: {e}")

# 在主循环中触发：
# t = threading.Thread(target=background_parl_update, args=(...))
# t.start() 
# 主线程直接往下走，无需在原地硬等 PARL 梯度计算完成！

```


2. **优化 `runner_LLM_new.py` 中的 Re-scoring 逻辑**：
* 检查 `Re-scoring accumulated data with PARL reward model` 部分，为历史样本引入字典缓存（Cache），**只对本轮新增的 rollout 样本计算 hidden states 并打分**，历史样本直接读取缓存分数，彻底消除重复前向计算。
